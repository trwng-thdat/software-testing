    design(hw5): select spec-verified profile + order-history workflow
    
    Workflow covering all three endpoint groups, every step verified against
    api_spec.md:
    
      1. POST /api/login           (1.2)  auth-heavy
      2. GET  /api/users/me        (2.1)  read-heavy
      3. GET  /api/orders/my-orders(4.4)  read-heavy
      4. PUT  /api/users/me        (2.2)  transactional
      5. POST /api/apply-coupon    (5.1)  transactional
    
    Chosen because no other group member tests FR-04 profile management;
    only POST /api/login overlaps, which is unavoidable since every
    auth-heavy journey needs a token.
    
    Adds correlation points (token, user id, order id), per-step assertions
    that check response bodies rather than status codes alone, and a
    three-file CSV design. users.csv is sized at or above the peak thread
    count with recycle=false so no two virtual users share a login, which
    keeps the FR-02 three-fail lockout from turning the error rate into a
    measurement of lockout instead of performance.
    
    Records the design in the audit report as artifacts #2 and #3. Artifact
    #2 is tagged INVALID: the first proposal named /api/profile and
    PUT /api/profile, routes that do not exist in the SUT. They were
    pattern-matched from the FR titles rather than read from the test basis
    (ISTQB FL 3.2.1). Supplying api_spec.md corrected them to /api/users/me.
    
    Three open items remain before the test plans can be built: confirm the
    my-orders and apply-coupon collision with teammates, verify whether
    apply-coupon persists anything, and locate the database lockout-reset
    path.
